# 功能规范 — 标书制作智能体

## 需求背景

传统的标书撰写流程存在以下核心矛盾：
- **效率瓶颈**：一份 2 万字的完整标书初稿撰写需要 3-5 个工作日，且大部分精力花在重复性的格式填充和基础内容组织上
- **质量不稳定**：人手撰写的标书常常遗漏评分项、格式不统一、前后数据矛盾，每次投标需要做大量人工校验
- **知识无法沉淀**：历史中标标书和优质模板缺乏系统管理手段，写标书时"翻旧文档"效率低下

AI 驱动的标书生成，不是"一键生成立即投标"，而是：
1. 把初稿生成从天级压缩到分钟级
2. 把人从低级重复劳动中解放出来，聚焦于审阅和策略优化
3. 把企业标书知识沉淀为可检索、可复用的数字资产
4. 支持基于反馈的精准微调，而非每次重写全文

## 用户故事

### 用户故事 1 - 上传资料并生成标书初稿（优先级：P1）

作为投标负责人，我希望把招标文件和相关资料上传后，系统能自动解析需求、匹配模板、生成一份结构完整的标书初稿，这样我就不需要从零开始逐章手写了。

**为什么这个优先级**：这是整个系统的最小可行产品。没有这个能力，其他功能（微调、导出、多模型）无从谈起。

**独立测试**：上传一份招标文件 PDF → 选择标书类型 → 点击「开始生成」→ 5-10 分钟内获得一份包含全部章节的标书初稿。

**验收场景**：
1. **给定** 一份服务类招标文件 PDF（约 80 页），**当** 用户上传文件并选择「服务采购」模板，**那么** 系统在 10 分钟内生成一份包含项目概述、服务方案、团队配置、实施计划、质量保障、应急预案、商务应答等全部章节的标书，每章不少于 500 字
2. **给定** 招标文件中包含 15 条评分标准，**当** 系统完成需求提取，**那么** 提取结果准确识别出所有评分项、分值和评审因素，遗漏率 < 10%
3. **给定** 上传了格式损坏的 PDF（扫描件），**当** 系统尝试解析，**那么** 系统提示用户该文件可能不可读并要求重新上传或手动输入关键信息

### 用户故事 2 - 审阅标书并提交反馈微调（优先级：P1）

作为投标负责人，在查看生成的标书初稿后，我希望能针对特定章节或段落提交修改意见，系统能精准修改目标位置而不影响其他内容。

**为什么这个优先级**：微调循环是本产品区别于「一次性模板填充」的关键差异化能力。初稿永远是粗糙的，微调让人的判断力成为质量保障的最后一道防线。

**独立测试**：在生成完成的标书上，选中「服务团队配置」章节第 3 段 → 输入"补充张三的项目经验"→ 提交反馈 → 系统针对该段落重写并保留上下文连贯性。

**验收场景**：
1. **给定** 标书第 3 章第 2 段落包含「项目团队配置」描述，**当** 用户提交反馈"补充项目经理张三年限和证书编号"，**那么** 系统仅修改该段落，重新生成的内容包含年限和证书信息，且前后段落未发生变化
2. **给定** 用户在同一章节提交了 3 轮反馈，**当** 查看版本历史，**那么** 系统展示每次修改的 diff 记录，支持回溯到任意历史版本
3. **给定** 用户提交了模糊反馈「整体太啰嗦了」，**当** 系统尝试解析，**那么** 系统请求用户指定具体章节或段落（不是猜测用户意图）

### 用户故事 3 - 质量检查与导出（优先级：P2）

作为投标负责人，在标书定稿前，我希望系统能自动检查标书的完整性和合规性，并能导出为符合招标格式要求的 DOCX 文件。

**为什么这个优先级**：质量检查是防废标的安全网。导出是交付环节的最后一公里。这两个功能在初稿 + 微调稳定后可自然追加。

**独立测试**：点击「质量检查」→ 系统输出完整性报告（列出遗漏的评分项）→ 修复遗漏后 → 点击「导出」→ 下载一份格式规范的 DOCX。

**验收场景**：
1. **给定** 标书完成了全部章节生成但遗漏了 2 条评分项，**当** 执行质量检查，**那么** 系统输出报告列出遗漏项所在评分条目的原文引述和对应应写的章节
2. **给定** 标书质量检查全部 PASS，**当** 点击导出 DOCX，**那么** 下载的文件包含自动生成的目录、连续的页码、正确的标题层级，字体为仿宋/黑体（符合政府采购格式要求）
3. **给定** 标书某章节出现「绝对的」「最优秀的」等禁用词，**当** 执行合规性检查，**那么** 系统标记违禁词位置并建议替换方案

### 用户故事 4 - 多模型供应商配置（优先级：P2）

作为技术使用者，我希望能在界面中选择不同的 LLM 供应商和模型，并为不同的任务（生成、检查、提取）配置不同的模型，这样我可以根据成本和质量需求灵活调配。

**为什么这个优先级**：多模型是差异化优势但在 Phase 1 可以先限定 1-2 家供应商打通全流程，其余逐步接入。

**独立测试**：在配置面板输入 OpenAI API Key → 选择 GPT-4o 作为生成模型 → 切换 Claude 作为质量检查模型 → 重新生成标书 → 验证各节点使用了正确的模型。

**验收场景**：
1. **给定** 用户输入了 DeepSeek API Key，**当** 选择 DeepSeek 作为默认模型并启动生成，**那么** SectionGenerator 节点使用 DeepSeek-Chat，其他未指定节点也使用 DeepSeek
2. **给定** 用户配置了「质量检查节点使用 Claude」，**当** 生成完成后自动触发质量检查，**那么** QualityChecker 节点使用 Claude，而 SectionGenerator 仍使用默认模型
3. **给定** 用户输入了无效的 API Key，**当** 点击「测试连接」，**那么** 系统返回连接失败及具体错误原因

### 用户故事 5 - FAISS 知识库检索增强（优先级：P3）

作为投标负责人，我希望系统能自动检索历史中标标书中的优质段落和表述，在生成新标书时作为参考，这样标书质量能持续进化，新标书复用已有成功经验。

**为什么这个优先级**：这是价值积累的长期引擎，但在 Phase 1 可以先从模板库单索引开始验证检索管线是否有效，历史标书库可以在后续阶段补充。

**独立测试**：上传 3 份历史中标标书 → 系统建立索引 → 新生成标书时自动检索相关段落 → 生成内容中融入了历史标书中的表述模式。

**验收场景**：
1. **给定** 历史标书索引中存有 5 份劳务管理类的服务方案，**当** 新生成一份劳务管理类标书的「服务方案」章节，**那么** 检索返回与当前章节最相关的 3-5 个历史段落并注入到生成 prompt 中
2. **给定** 模板库已有 6 种标书类型的各 3 套模板，**当** 用户选择「系统集成」类型，**那么** TemplateMatcher 返回前 3 匹配模板，匹配准确率 > 80%

## 成功标准

| 指标 | Phase 1 目标 | 测量方式 |
|------|-------------|---------|
| 标书生成完整率 | > 90%（章节无遗漏） | QualityChecker 评分项覆盖率 |
| 需求提取准确率 | > 90%（评分项遗漏率 < 10%） | 人工对比招标文件原文 |
| 初稿生成时间 | < 10 分钟（8 章约 20,000 字） | 系统计时 |
| 微调循环可用性 | 至少完成 2 轮精准微调 | 人工验证修改范围 |
| 质量检查自动发现问题 | > 80% | 与人工审查结果对比 |
| 模板匹配准确率 | > 80%（Top-3 命中） | 人工评估匹配结果 |
| 至少支持 2 家 LLM 供应商 | DeepSeek + OpenAI | 端到端测试 |
| 支持 6 种标书类型 | 服务/货物/软件/工程/集成/运维 | 各类型至少 1 份完整生成 |

## 边界条件与约束

- **只做初稿**：系统只生成标书初稿，最终定稿和策略决策由人工完成
- **不存储 API Key**：LLM API Key 在内存中暂存，不持久化到磁盘或数据库
- **不涉及评标决策**：不分析竞争对手、不建议报价策略、不预测中标概率
- **Phase 1 仅单用户**：不考虑多用户、权限管理、账户体系
- **数据不出本地**：Phase 1 所有数据在用户本地，不涉及云端上传
- **离线能力受限**：LLM 调用必须联网（依赖用户 API Key），FAISS 索引可在本地构建

## 不包含的功能（明确排除）

- ❌ 自动投标提交或招标平台对接
- ❌ 竞争对手分析与报价策略建议
- ❌ 多用户协作与权限管理
- ❌ 移动端或小程序
- ❌ 语音输入反馈
- ❌ 模板在线市场或社区共享
- ❌ Phase 1 内完成商业化功能（计费、账户、License）

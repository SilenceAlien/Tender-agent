# 软件开发类标书提示词模板

## 类型核心特征

软件开发采购的核心是 **「需求理解 + 架构决策 + 过程管控」** 。评标委员会最关注：
- 是否真正理解了业务痛点（不是复述招标文件）
- 技术架构是否合理且可演进（不是堆砌技术名词）
- 开发过程是否透明可控（不是黑盒交付）

**风格导向**：技术精确、逻辑自洽、过程可审计。每个技术选型必须说清「为什么选这个而不是那个」。

**信创合规提示**：政府采购的软件开发项目通常涉及信创（国产化）要求。如果招标文件提及「安全可控」「国产化」「信创」等关键词，本章节必须自动激活信创适配要求。

## 统一评分框架映射

| 标准评分维度 | 软件开发对应章节 | 典型权重 | 高分关键 |
|-------------|----------------|---------|---------|
| 整体方案设计 | 需求理解与分析 | 10-15% | 用自己语言重述需求 + ≥3个增值建议 |
| 关键技术方案 | 技术架构设计 | 25-35% | 分层架构 + 选型理由 + 非功能指标量化 |
| 项目实施计划 | 开发实施计划 | 15-20% | 分阶段交付 + 里程碑可验证 + 风险清单 |
| 项目团队配置 | （独立章节） | 10-15% | 关键角色简历 + 同类项目经验 + 证书 |
| 培训与运维 | 运维与知识转移 | 5-10% | 交付文档清单 + 分层培训 + 源码交付 |
| 质量安全保障 | 质量保障与测试 | 5-10% | 测试分层 + 缺陷管理流程 + 安全设计 |

## 废标风险清单

| 风险项 | 检查点 | 后果 |
|--------|--------|------|
| 软件资质缺失 | CMMI/ISO9001/ISO27001/ITSS等是否在有效期内 | 资质分扣减或资格审查不通过 |
| 信创不合规 | 未提供信创适配方案或兼容性证明 | 技术方案审查不通过 |
| 等保要求缺失 | 系统需达到等保三级但方案未体现安全设计 | 安全审查不通过 |
| 业绩不匹配 | 同类软件开发案例不符合招标文件要求（规模/行业/金额） | 业绩分扣减 |
| 核心人员缺失 | 项目经理无PMP/高项证书或核心开发人员资格不满足 | 团队分扣减 |
| 知识产权模糊 | 源码归属/第三方组件许可未说明 | 合同风险 |

## 章节提示词

### 一、需求理解与分析

```
你是需求分析师。请撰写「需求理解与分析」章节：

【约束】
- 用自己的语言重新梳理客户需求，证明你「看懂」了业务，而非复制招标文件
  → 标准：如果删掉本节，你的理解不会在招标文件中找到原文——这才叫「理解」
- 对招标文件中模糊、矛盾或遗漏的需求点，给出你的分析和假设，标注「建议澄清」
- 从业务视角提出 ≥3 个招标文件未明确但实际必需的功能点，标注「增值建议」
- 每个增值建议必须说明：为什么需要 + 带来的业务价值 + 实现思路（1-2句）
- 禁止：全盘复述招标文件（零信息增量 = 零价值，评审会直接跳过低分处理）
- 禁止：需求理解中涉及技术实现细节（如「用Redis缓存用户数据」）
- 必须：如果你在该行业有经验，用业务术语而非技术术语描述需求
- 风格：顾问式咨询报告，展现行业洞察
```

### 二、技术架构设计

```
你是系统架构师。请撰写「技术架构设计」章节：

【约束】
- 架构必须分层描述，每层说明：职责 + 技术选型 + 选型理由：
  → 基础设施层（服务器/网络/存储/云资源）
  → 数据层（数据库/缓存/消息队列/数据湖仓）
  → 服务层（微服务/API网关/服务治理/中间件）
  → 应用层（业务模块/公共组件/工作流引擎）
  → 展现层（前端框架/多端适配/UI组件库）
- 每个技术选型必须三段论证：「选了什么 → 为什么选它（至少2个理由） → 否决了什么替代方案（为什么）」
- 非功能性需求必须量化（不能被量化的需求 = 无法验收的需求）：
  → 并发量：峰值并发用户数，基准测试数据支撑
  → 响应时间：P50/P95/P99 分别承诺，附压测条件说明
  → 数据量：当前数据量、年增长率预估、3年数据容量规划
  → 可用性：如99.9%（年度允许宕机≤8.76小时），附实现机制
  → 安全：等保等级目标、密评等级目标、数据分类分级方案
- 如涉及新旧系统衔接，必须独立描述：数据迁移策略 + 接口对接方案 + 切换过渡方案
- 信创适配（如触发）：在每层架构说明中标注信创替代方案和兼容性验证状态
- 禁止：堆砌技术名词而无选型论证——「采用微服务+容器化+大数据+AI中台」= 零分
- 禁止：非功能指标写「满足用户需求」——必须给具体数字
- 风格：架构设计决策记录(ADR)，每个决策可追溯
```

### 三、开发实施计划

```
你是项目经理。请撰写「开发实施计划」章节：

【约束】
- 分阶段交付，每阶段四要素：交付功能 | 交付物清单 | 验收标准（量化） | 计划时间
- 开发方法论说明（如敏捷）：
  → 迭代周期时长（2周/3周）
  → 每个Sprint的产出物（可运行增量+测试报告+Sprint评审记录）
  → 甲方参与机制（Sprint评审会/需求优先级排序/变更管理流程）
- 里程碑定义用可验证标准：
  → 反例：「系统基本可用」——不可验证
  → 正例：「UAT测试通过率≥95%，所有P0/P1缺陷关闭，性能测试TPS≥招标要求」
- 人员投入计划：按阶段列出角色配置和人天估算
- 风险管理：列出 ≥5 个具体风险，每个用「风险描述 → 概率 → 影响 → 应对措施」四要素
  → 必须包含：需求变更风险、关键人员离职风险、第三方依赖风险、性能不达标风险、信创适配延期风险（如适用）
- 禁止：「加强管理」「专人负责」——必须有具体机制描述
- 风格：甘特图语言描述 + 里程碑验收条件表
```

### 四、质量保障与测试

```
你是测试负责人。请撰写「质量保障与测试」章节：

【约束】
- 测试策略分六层，每层说明：范围 | 工具 | 通过标准 | 执行人：
  → 单元测试（覆盖率≥80%，核心模块≥90%）
  → 集成测试（API测试+接口契约验证，覆盖所有端点的正常/异常/边界）
  → 系统测试（功能测试+兼容性测试，覆盖所有用户场景）
  → 性能测试（压力测试+负载测试+稳定性测试，提供测试报告模板结构）
  → 安全测试（代码安全扫描+渗透测试+等保差距分析）
  → 验收测试（UAT，甲方主导，通过标准双方确认）
- 缺陷管理全流程：发现（填写模板） → 分流（P0-P3分级标准） → 修复（指派+时限） → 回归（关联用例） → 关闭（甲方确认）
- 代码质量管控：代码审查机制（所有PR需审查人Approval）+ 静态扫描工具 + 编码规范清单
- 禁止：一笔带过「进行全面测试确保质量」
- 禁止：测试通过标准写「测试通过」——必须是可验证的条件
- 必须：测试报告模板结构描述（便于甲方预知交付物形态）
- 风格：测试主计划书，可执行可审计
```

### 五、运维与知识转移

```
你是运维负责人。请撰写「运维与知识转移」章节：

【约束】
- 免费运维期明确：起始日（验收合格之日起）| 时长（≥12个月）| 服务内容清单
- 运维SLA分级：
  → 故障响应：P0-30分钟/P1-2小时/P2-4小时/P3-8小时
  → 故障解决：P0-4小时/P1-8小时/P2-24小时/P3-72小时
  → 不达标罚则：每次超出时限的扣款计算方式
- 交付文档清单（不少于 6 类）：
  → 系统设计文档、数据库设计文档、API接口文档、部署运维手册、用户操作手册、源码说明文档
- 培训分三层：系统管理员（技术培训）、业务管理员（配置培训）、最终用户（操作培训）
  → 每层说明：课程内容摘要、课时、形式、人数上限
- 源码交付：明确交付范围（全部源码/部分模块）和知识产权归属（甲方所有/双方共有/授权使用）
- 禁止：只说「提供完整文档」不列清单——验收时甲方无法逐项验收
- 必须：文档交付物的内容结构做简要描述（如「API文档包含接口路径、请求参数、响应格式、错误码说明」）
- 风格：交付清单式，逐条可验收
```

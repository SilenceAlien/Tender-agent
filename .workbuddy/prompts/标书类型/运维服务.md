# 运维服务类标书提示词模板

<!-- 预估 tokens: ~900 | 加载条件: 用户明确这是运维/维保/持续服务类项目 -->

## 类型核心特征

运维服务采购与项目型服务采购的根本区别：**运维是「持续保障」而非「一次性交付」**。评标委员会最关注：
- 能否在长达 N 年的服务期内持续稳定交付（不是投标时的承诺表态）
- SLA 指标是否可测量、可考核、有罚则（不是模糊承诺）
- 应急响应是否有真实可执行的预案（不是套模板）

**风格导向**：SLA 驱动，指标化，可审计。每个承诺必须有对应的测量方式、报告机制和违约罚则——没有罚则的 SLA 等于没有 SLA。

**与其他模板的关系**：服务采购模板侧重「项目交付型服务」（有明确起止的一次性项目），本模板侧重「持续运维型服务」（按年计费的稳态服务）。混合项目可叠加使用。

## 统一评分框架映射

| 标准评分维度 | 运维服务对应章节 | 典型权重 | 高分关键 |
|-------------|----------------|---------|---------|
| 整体方案设计 | 运维服务体系 + 服务内容 | 20-30% | ITIL落地框架 + 量化服务目录 |
| 关键技术方案 | SLA服务等级协议 | 15-25% | 指标量化 + 测量方式 + 罚则公式 |
| 项目实施计划 | 应急预案与灾备 | 10-15% | 场景化预案(≥5个) + RTO/RPO |
| 项目团队配置 | 服务体系（人员部分） | 10-15% | 证书 + 同类运维经验 + 驻场安排 |
| 培训与运维 | 持续改进机制 | 5-10% | PDCA闭环 + 知识库 + 变更管理 |
| 质量安全保障 | 应急预案 + SLA（安全指标） | 5-10% | 事件分级 + 灾备验证 |

## 废标风险清单

| 风险项 | 检查点 | 后果 |
|--------|--------|------|
| 运维资质缺失 | ITSS运维资质/ISO20000/ISO27001等是否在有效期内 | 资格审查不通过或大幅扣分 |
| SLA承诺矛盾 | 不同章节对同一指标的承诺值不一致 | 诚信风险 |
| 备件清单为空 | 有硬件维保但未提供备件清单和库房信息 | 方案不完整 |
| 人员证书水分 | 关键岗位证书过期或不可查 | 团队分扣减 |
| 异地服务能力不实 | 承诺全国服务但无分点证明 | 履约能力质疑 |

## 章节提示词

### 一、运维服务体系

```
你是运维服务负责人。请撰写「运维服务体系」章节：

【约束】
- 服务体系按 ITIL/ISO20000/ITSS 框架组织，但关键是落地方式而非标准名称
  → 反例：「本方案基于ITIL最佳实践」——没有任何信息量
  → 正例：「服务台采用ITSS一级标准，通过XX工单系统实现事件管理全流程闭环，包括：事件登记→分类定级→分派→处理→关闭→满意度回访」
- 组织架构四层级，每层说明职责和值守方式：
  → 运维经理（总体协调+客户接口+重大事件决策）
  → 专业组长（网络/系统/安全/数据库，各组长说明技术深度）
  → 一线工程师（排班方式+技能矩阵）
  → 二线专家支持（厂商/原厂支持渠道和响应机制）
- 服务台核心要素：服务时间(7×24或5×8+oncall) | 接报渠道(电话/邮件/工单/微信) | 升级机制(一线→二线→三线的触发条件和时限)
- 驻场还是远程必须明确：
  → 驻场模式：驻场人数+排班表+驻场办公条件需求
  → 远程模式：VPN接入方式+远程监控工具+定期巡检安排
- 运维边界用 RACI 矩阵说明：哪些是运维负责(R)、哪些是甲方负责(A)、哪些需要协作(C)、哪些需要厂商负责(I)
- 禁止：只画组织架构图而没有职责说明——评审不会看图脑补
- 禁止：不写运维边界——等出了故障才发现「这个不在合同范围内」
- 风格：运维手册式的制度描述，读完能直接作为运维团队的入职培训材料
```

### 二、SLA 服务等级协议（核心章节）

```
你是服务质量经理。请撰写「SLA服务等级协议」章节：

【约束】
- 逐条列出服务指标，每条必须包含六要素：
  指标名称 | 指标定义（公式） | 目标值 | 测量方法 | 数据来源 | 违约罚则（公式）
- SLA 指标至少覆盖以下五类，每类 1-3 条：
  → 响应指标：响应时间（从接报到开始处理）| 解决时间（从接报到解决并关闭）
  → 可用性指标：系统可用性（计算公式：正常服务时间/总服务时间×100%）| 核心业务可用性
  → 质量指标：首次解决率（一线工程师独立闭环比例）| 数据完整率 | 备份成功率
  → 安全指标：安全事件响应时间 | 漏洞修复时限（按危险等级分级）
  → 满意度指标：服务满意度评分 | 投诉处理时限
- 事件分级标准（P0-P3 级），每级不同的响应和解决时限：
  → P0-致命：核心系统瘫痪，影响全部用户 → 响应≤15min / 解决≤4h
  → P1-严重：核心功能异常，影响大部分用户 → 响应≤30min / 解决≤8h
  → P2-一般：非核心功能异常，影响部分用户 → 响应≤2h / 解决≤24h
  → P3-轻微：个别问题，不影响主要业务 → 响应≤8h / 解决≤72h
  → 注意：值根据项目实际调整，不要盲目承诺低于行业底线的时限
- 考核周期和扣款计算方式明确：
  → 考核周期：月度/季度
  → 扣款公式示例：「月度可用性 < 99.9%，每低0.01%扣减月度服务费X%」
  → 「基础指标」（不达标扣款）和「挑战指标」（达标奖励）区分策略
- 禁止：SLA只写承诺不写罚则——没有罚则的SLA在评审眼里等于没写
- 禁止：承诺超出行业常识的指标
  → 如「可用性100%」「0秒响应」——评审会觉得你不专业
- 必须：每条指标的可测量性审一遍——「这个数据从哪来？谁来记录？」
- 风格：合同级严谨，指标公式化，每条可直接写入运维服务合同
```

### 三、运维服务内容

```
你是运维服务策划人。请撰写「运维服务内容」章节：

【约束】
- 服务内容按频次分三层组织：
  → 日常运维（每日/每周）——每项列出：巡检项目 | 操作内容 | 执行时段 | 输出物（如巡检报告）
  → 定期维护（月度/季度/年度）——每项列出：维保对象 | 维保内容 | 维保窗口(对业务影响最小时段) | 风险告知流程
  → 专项服务（按需/定期）——如深度健康检查、性能调优、容量规划、安全加固、应急演练
- 服务目录格式：「服务项名称 | 服务描述(1-2句) | 频率 | 执行人角色 | 输出物 | 甲方审批要求」
- 硬件维保必须说明备件保障：
  → 备件库位置和覆盖半径
  → 备件清单(名称/型号/数量/单价)
  → 备件更换时限(按故障级别分级承诺)
  → 停产物料的替代方案
- 软件维保说明版本升级策略：小版本(修复)自动升级 | 大版本(功能)评估后升级 | 安全补丁响应时限
- 禁止：「按需提供运维服务」——这句话在合同中=没有责任
- 禁止：输出物只写「巡检报告」不描述报告包含什么——甲方不知道你交付什么
- 必须：每项服务内容对应对一个可检查的输出物——方便甲方验收
- 风格：服务日历 + 服务目录，读完能作为甲方监督运维的检查清单
```

### 四、应急预案与灾备（最容易翻车——写不好直接暴露运维经验不足）

```
你是应急管理负责人。请撰写「应急预案与灾备」章节：

【约束】
- 按故障场景逐一写预案，不少于 5 个场景，每个场景按统一结构：
  → 触发条件（什么现象触发响应？如：数据库服务不可达持续超过1分钟）
  → 影响评估（影响哪些系统、哪些用户、业务损失预估范围）
  → 响应流程（分步写，每一步标注责任人角色和执行时限）
  → 恢复目标：RTO（恢复时间目标，业务中断时长上限）和 RPO（恢复点目标，数据丢失量上限）
  → 事后复盘机制（根因分析+改进措施+知识库录入）
- 必须覆盖的场景（根据项目实际增减）：
  → 硬件故障（服务器宕机/存储故障/网络设备故障）
  → 软件故障（应用崩溃/数据库损坏/中间件异常）
  → 数据问题（数据丢失/数据损坏/误删除）
  → 安全事件（勒索软件/数据泄露/DDoS攻击）
  → 环境故障（机房断电/空调故障/火灾/漏水）
- 应急演练计划：频率（至少1次/半年）| 方式（桌面推演+实战演练）| 参与方 | 演练后输出
- 灾备架构：备份策略（全量/增量/实时同步）| 备份周期 | 异地备份说明 | 恢复测试频率
- 禁止：预案写成「立即联系相关技术人员处理」——这是最差的应急方案
- 禁止：预案中出现「视情况而定」——应急就是要在不确定中给出确定的行动路径
- 必须：预案让评标专家感觉「这帮人真处理过类似故障」
  → 标准：预案中的步骤细节多到让人觉得不可能是编的——比如「登录XX管理平台，执行show processlist定位阻塞SQL」
- 风格：故障场景剧本式，每个场景可独立演练
```

### 五、持续改进机制

```
你是运维质量负责人。请撰写「持续改进机制」章节：

【约束】
- 月度/季度运维报告内容结构必须描述（不是「提交运维报告」一笔带过）：
  → 本期服务概况（事件数/问题数/变更数/完成率）
  → SLA达成情况（每条指标的达成值和趋势图描述）
  → 重点事件回顾（TOP3事件的分析和处理过程）
  → 改进计划和下期重点
- 问题管理全流程闭环：发现→记录→分级→根因分析(RCA)→改进措施→实施→验证→关闭
  → 重点是：根因分析方法论（5 Whys/鱼骨图/故障树），不是一句「分析原因」
- 变更管理全流程：申请→评估（风险/影响范围/回滚方案）→审批→实施（窗口/步骤）→验证→回顾
- 知识库建设：故障案例库的结构、操作手册的更新机制、FAQ的维护方式
- 禁止：「不断提升服务质量」——这是口号不是机制
- 必须：所有流程有闭环——每个环节有输入→处理→输出→下一环节
- 风格：PDCA 循环式的流程描述，每个流程可审计
```
